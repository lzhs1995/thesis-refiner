# 完成消息已到达，但执行者仍在等待

共享[接收端绑定契约](receiver-bound-delivery.md)约束本页全部投递判断：输入前
固定原生 session、transcript inode、日志边界及完整 payload；仅原次之后同一
绑定 journal 内整条相等的原生消息证明收到。Claude `queued_command` 只证明
客户端接受，不能证明执行或完成；ACK、屏幕 DONE 和活动均不作送达证据。

## 故障分类与责任

原执行者反复输出 `REPORT_READY ... CALLBACK_UNCONFIRMED` 时，先核报告、原回调尝试、主管原生入站及后继回执。若已收到 DONE 但仍缺结算、产物核收或该任务 marker 的解除，才属于主管收尾未完成；这不是 API 死亡，也不触发连续 300 秒 API 失败规则。

恢复责任由主管承担。不得让用户手工转发已可通过受保护通道取得的消息；不得让已完成报告的执行者重复发送、重启会话、清空上下文、换模型或继续制造测试来等待回执。

Stop 的 prompt/agent 辅助 evaluator 报模型不可用时，分别核实际事件、handler、配置来源与主会话的模型及请求。辅助检查错误不计入主模型 API 失败时钟，也不授权换主模型、重启原会话或停用全部 Hook；修复范围只限已定位的辅助入口。主执行者可用性仍按[既有连续失败规则](collaboration-and-recovery.md)裁定：至少连续 300 秒真实失败、门槛后的新鲜失败，以及真实成功重置计时均保留，静屏或排队不能代替。

## 一次有界收尾

1. 原 callback 的完整原生入站到达时优先处理：核原 task/nonce、双方 UUID、任务包和报告哈希、输入前绑定的 session/transcript inode 及原次之后的整条相等 payload。若回执已有且有效，直接消费，不重复结算。
2. 缺回执时只调用原任务版本支持的接收端结算接口；真实当前 caller、原 journal 和原锁必须一致。屏幕已滚出时使用原始原生 user 记录，不能凭摘要或工具输出伪造。
3. 独立读报告、原产物与未决项，另记主管裁定。传输已确认不代表业务验收、资源释放或论文终验。
4. 达到任务终态后精确 disarm 该 task marker，保留其他任务。一次必要的恢复通知也须绑定独立原 attempt，unknown 只读核原次，不重贴或创建新 nonce；不增加“通知的通知”或新的 ACK 门禁。原回调已真实确认且完成上述裁定与收尾后，停止该任务的回调探针；后续辅助入口维护另列。
5. 验证原执行者真实回复；有独立待办才派下一个有界任务，保留同一会话身份。实际新回复/工具调用是恢复证据，配置修改和测试通过各自记账。

## 已收口后仍复述旧状态

原回执、业务裁定和精确解除记录均有效时，不再重做上面的结算或 disarm。
执行者在后续用户提示后新增回复，却仍引用旧 `CALLBACK_UNCONFIRMED`，应记为
状态叙述未更新；不能把它说成没有任何回复、当前 hook 封锁或连续 API 故障。
原 attempt 中的传输失败观察仍保留，由后继回执说明收口，不覆盖历史失败。

可用性文件的 `ACTIVE` 与任务生命周期不同；该契约没有完成态时，不手工增添
状态来使页面看似一致。主管的一次通知给出三份真实证据及下一动作；原 marker
已解除后，原会话可按这次授权读指定证据、回答当前状态。若仍有实际工具拒绝，
核拒绝原文和实际加载入口，不凭旧复述反复安装技能。通知消费、真实工具调用、
下一任务执行和论文原生交付分别记录；无新独立待办时允许等待主线依赖。

## finalized 不等于已执行

任务包冻结只表明内容确定。区分原派发证明零输入、已提交/排队、已消费、已报告、已回调、已验收。缺记录不是零输入；存在业务报告或回调尝试时不能仅靠某次派发的 NO_INPUT 推断业务未运行。若实现允许未派发任务结束，其证据应绑定真实 caller/workspace/目标及包哈希，保持原锁和日志稳定；未知仍拒绝，绝不生成虚假回执或释放资源。

## 双 Claude 如何提高效率

共享代码只设一个写入者，另一位审不同的未决边界；主管推进主任务并负责核收。没有独立待办时允许已完成者空闲，不能为“两个窗口都动”重复审已通过结果。同 pane 输入串行，后台计算可并行。

恢复工单分别记录：现场现象、原始原因证据、零输入核收、业务裁定、精确 marker 收尾、原会话恢复、源代码测试、GitHub 提交、实际安装。一次恢复不承诺永久无故障。维护不启动新统计、不重放成功的 Zotero Refresh、不替代最终 Word/PDF 验收。
