# NLM 同账号认证与传输恢复

健康任务继续复用原绑定，不为方便而登录、导航或更换后端。已有证据确认原认证或传输失效时，先区分故障层，再按用户现有恢复授权推进；已经授权同账号恢复，不重复向用户索取同一项许可。这里不授予换账号、绕过额度、清理其他会话或重发原请求的权限。

反复连接失败先走 [连接诊断与自动接续](nlm-connection-recovery.md)。`proxy.start_tls.failed` 且源站请求尚未开始属于连接层；代理 CONNECT 的 HTTP 200 只表示隧道建立。它们不能证明 Google 认证失败，不先做反复登录。恢复决定的 `JSONDecodeError` 则先检查本地证据类型，使用预检工具，不发新的探针题。

## 先判断故障属于哪一层

| 实际证据 | 能支持的判断 | 不能推导的结论 |
|---|---|---|
| 已绑定 CDP 端口或 target 消失 | 原传输不可用，需要核实进程与原请求 | 账号被封、必须换账号、原请求已完成 |
| 本地 cookie 文件可解析或数量非零 | 缓存存在 | 当前身份认证仍有效 |
| 请求沿重定向进入登录页，或认证端明确 401 | 该认证路径失败 | 通用 RPC 限流，或所有 Google 服务都不可用 |
| 登录页面有实际会话字段，SDK 却报字段缺失 | 可能是版本相关解析问题，需核原字段与解析器 | 立即再次登录或清 profile |
| HTTP 200 空答、状态 unknown、没有引用 | 保留该响应的实际缺口和查询健康状态 | 自动归因于账号风控、官方并发上限或认证过期 |

先使用已绑定路径的最窄身份验证；每次网络验证仍需当前资源准入。泛用 CLI 的 `status`、本地配置检查或 cookie 数不能代替带网络验证的身份检查。认证成功、查询健康恢复、音频可生成是三个判断，不能互相代替。

## 在安全边界恢复原账号

1. 由一个已明确的恢复所有者接手；核原请求终态、预算/队列与实际锁，保留所有失败和未知记录。认证恢复不能清掉旧 UNCERTAIN，租约过期也不证明可抢占。
2. 优先使用原 profile 支持的静默刷新，并保存实际响应。刷新失败后核明原因；不要按固定次数不断撞同一个 401。需要浏览器恢复时，复用原保存的账号/profile，先检查当前版本的登录助手会不会顺带扫描、清 profile 或关闭其他 Chrome。
3. 原 target 消失而既有授权涵盖恢复时，可在任务私有范围建立新的实际传输绑定。先验证恢复的是原账号，再保存凭据；不使用 force 覆盖不同身份。默认 profile/全局 notebook 选择不为任务便利而切换。
4. 只回收本次自己启动且身份明确的辅助进程，保留复用浏览器和其他会话。以实际退出、原调用终态和锁可取放为归还依据。
5. 保存旧绑定和失败证据，新 binding 记录实际 backend、target 或 HTTPS 端点、工具版本与哈希，以及原账号匹配证据。HTTPS 入口不伪填不存在的 CDP target；旧已固定的 runtime/transport 不原位热改。
6. 向当前协调者交新绑定与实际归还证据，再接续原计划中尚未发送的必要操作。恢复成功不重置调用消耗、恢复决定或查询暂停；查询恢复仍按既有单题健康规则处理。

## 有原始证据才修解析兼容性

已观察到 `notebooklm_tools` 0.9.12 的一个会话字段解析器只接受无符号数字，而实际 `FdrFJe` 可以带负号，表现为 `MISSING_AUTH_TOKENS`。核对原页面字段后，任务私有适配层兼容有符号数字可恢复提取。这是该版本和该字段的具体兼容问题，不能泛化为所有 NLM SDK 的认证修复。

遇到此类问题，保留原失败，测试正数、负数、字段缺失及错误页面；不能仅为消除报错填一个会话值或放宽账号校验。不要把章节专用补丁自动写进共享 SDK，或假定上游尚未修复。通用 skill 记录识别方法，精确页面/凭据只保存在私有任务目录。

上述恢复不要求重新审论文或重新创建已经有 ID 的音频。原任务的预算、来源、去重与完成条件保持，后续按 [音频流程](nlm-audio-overview.md) 或 [审查流程](nlm-review-and-budget.md) 继续。
