# NLM 连接诊断与自动接续

目标是让原任务继续完成。已有恢复授权时由原执行者自动处理，不反复询问同一许可，不创建替代会话。保留原账号、来源、请求和论文范围；使用现成证据能解决的事项先离线处理。查询健康、网络归还、来源完整性与论文验收分别记录。

## 先定位故障层

| 原始证据 | 判断与下一步 |
| --- | --- |
| `proxy.start_tls.failed`，原跟踪显示源站 headers 未开始 | 代理隧道后的 TLS 握手失败；保留证书错误链、时间、原主机与代理配置。核原终态后只做同路 TLS 诊断。不能据此认定认证过期。 |
| CONNECT 的 HTTP 200 | 仅代理同意建立隧道；检查其后的目标 TLS 和源站响应，不能写成 NLM HTTP 200。 |
| 源站 headers/body 已开始，随后超时或断流 | 已进入提交后恢复；保存 UNCERTAIN，按[原会话状态与历史核收](nlm-stream-interruption-recovery.md)读取原流、原会话和进程证据，禁止自动重 POST。 |
| 本地无字符计时器到期并取消读取 | 能证明本地停止接收，不能证明服务端断网或终止。保留原流与未知终态；后继可显式采用无进展告警、有限总期限的同一读取等待器，不热改进行中的请求。 |
| 历史读取发生 TLS ConnectError，未取得 HTTP 响应 | 历史结果为未取得，不能写成空历史。原会话身份和已提交 query 保持；在真实恢复窗口内做已授权的有界只读核收。 |
| 请求窗口内有接口 INACTIVE、原地址移除、换网及新地址绑定 | 已证实本机网络发生变化；与请求开始/错误按统一时区关联。保留已提交请求，先核原会话，不能据换网自动当作零发送或认证失效。 |
| 实际登录重定向或源站 401 | 沿原账号/profile 做已有授权的认证恢复，见 [认证恢复](nlm-auth-recovery.md)。 |
| 源站 403 | 访问被拒绝，具体原因依原响应；不自动等同于认证或配额。 |
| 源站 HTTP 200，业务载荷为 `REGION_NOT_SUPPORTED`，可能含 `region_code` | 传输成功但业务被拒绝。保存完整原载荷与服务识别地区，核实际代理路线；不当成空答、认证过期或额度耗尽，不重复提交原 query。 |
| 源站 429 或明确额度提示 | 同账号暂停，按原提示条件使用一条必要任务恢复。不能用换账号、改 default 或反复登录处理。 |
| 原答完整、HTTP 200、零原生引用 | 请求已完成，属于引用/审读缺口。核原始帧是否漏解析；没有原生引用时按真实范围定向补审。 |
| source READY，但全文漏脚注、公式或图中文字 | 来源解析与覆盖问题；逐项列缺口，不能当成连接故障反复重传。 |
| 恢复决定报 JSONDecodeError | 本地输入/证据格式问题。脚本和日志可能被误作 JSON，先预检，不能再消耗一题验证。 |
| 首批校验报 `FAIR_NEXT_IDS_DIFFER`，且原证据证明尚未 claim/POST | 本地调度预期与当前公平选择不同；读取实际队列、容量和这次应选的 ID，修原私有启动器后只续未提交 READY。不能据此重试网络、重复入队或把本地失败算成新 query。 |

## 原执行者的连续恢复流程

1. 从当前 journal、队列、原流和进程证据定位最后已发送的请求。暂停新的故障路径准入，继续不受影响的本地裁决和交付。保留每次连接尝试；零字节 HTTP 文件、进程退出或租约到期单独都不是“未发送”证明。
2. 若完整原始跟踪证明每次都在源站 headers 前失败，并已核本批流、进程和锁真实结束，由原协调器据原 ID 归还/对账。没有远端答复就保留 `raw_answer=null` 或明确的缺失字段，不能造一个空 JSON 冒充响应。原 FAILED、UNCERTAIN 历史和调用消耗保持；已记账失败 ID 不复用。
3. 若仍需确认连接，沿实际绑定的主机、代理、SSL 验证、解释器和依赖做一次 TLS-only 诊断。默认只做原参数；有明确比较目的时最多四个指定 case。TLS 后立即关闭，0源站 HTTP、0凭据读取、0query、0上传。诊断由原协调器在已有资源边界运行；无需为此另开 NLM 测试题。
4. 形成一条 `FIXED_SINGLE_RECOVERY_DECISION`，绑定最新暂停失败、新证据和原计划里一条未提交的必要请求。先用恢复预检工具检查全部附件与字段，再在真实边界重新读状态、核原 READY/预算/锁，按原 journal `recover`→`admit` 执行。没有新依据时不循环恢复，不清日志或手改 `recovery_claimed`。
5. 这一必要请求收到完整真实答案、满足原生引用/来源契约并真实归还后，才恢复既有容量和公平队列，自动继续尚未提交的任务；本地逐项裁决并行。恢复失败继续保留暂停与原证据。无需等人反复发送“继续”。

提交后断流另有一项已验证经验：完整 HTTP 200 响应头、较大的接收字节数和标为答复类型的帧，都可能仍只有思考/搜索材料。原会话 ID、返回的 conversation ID 和 turn ID 分别保存；用当前原始请求体哈希核实状态接口所需身份。真实 IDLE 与已结束的本机调用共同支持归还；空历史只说明未取回答案。不能把前一次 TLS 恢复成功或普通 RPC 成功沿用为这一次长答恢复成功。

仅连接阶段、明确源站 headers 尚未开始的有界连接尝试，与重发已提交 POST 分开。保留原执行器已经验证的连接策略；不要把 retry 范围扩大到认证、读取超时或不明流状态。TLS-only 对照全部成功只说明当下连接可用，不能认定 ALPN、async、代理节点或 Google 风控是历史根因。禁用证书验证或任意切换全局代理不是恢复方案。

## 地区拒绝与任务路线固定

地区拒绝以服务实际响应为准。已经观察到 HTTP 200 载荷含 `REGION_NOT_SUPPORTED / region_code=CN`；该记录只证明该次操作被服务按此地区拒绝，不证明全部故障同因。代理监听端口、节点标签与服务识别出口分别核实；相同端口可能由不同进程或动态策略提供不同出口。

沿原任务绑定只读核查实际监听进程、控制 socket、使用的配置与连接路由。已有用户授权的恢复可以采用任务私有、明确绑定的可用路线，避免共享 selector 漂移；不要为一个任务修改全体代理、关闭 TLS 验证、换账号或重置额度。配置、依赖与执行器身份落在私有任务证据里，公开 skill 不写账号、机器地址和节点凭据。

路线确认后先核收原已提交请求：原 session 状态与历史的 HTTP 状态、完整 RPC、实际值分别保存。真实 IDLE 与本机调用结束才支持原协调器归还；history 为 `[]` 只证明未取回答案。一次状态/历史读取成功不证明长答成功。按现成恢复决定用一条已授权、尚未提交的必要题取得完整答案和原生引用，再自动续原队列。保留从原失败、路线观察到后继实际结果的时间与身份链。

有界连接尝试只接受完整 trace 证明全部失败均发生于源站 headers 开始之前；异常名称、零字节文件、HTTPX 报错类型或字符串包含 TLS 都不够。优先复用本文的离线分类契约，不能将简略的私有 retry 包装器直接推广为通用方案。收到源站响应后断流，仍走原 session 核收，禁止重 POST。一次真实长答在约178秒断流，早于等待器总期限且未触发本地无字符取消；延长等待不会修复该类原传输错误。

## 文件来源中断先定位已完成阶段

保存注册 source ID、上传会话、文件字节传输、处理状态与全文验收的独立原始记录。即便高层 `source_add` 返回失败，也可能已真实注册来源。先核 SDK 路径、完整 HTTP 记录及原操作终态，不以高层失败码把所有阶段都当作未发送。

本地第二客户端构造失败且证据证明上传请求未开始时，原协调者可在既有授权和新鲜安全边界沿原 source ID 接续唯一未提交的上传阶段；不重复注册、不覆盖原 FAILED。若上传会话或文件数据已可能提交，先核原会话/来源状态，不能用这条规则重新发送未知操作。对应离线检查见 [文件来源的多客户端预检](runtime-validation.md#文件来源的多客户端预检)。

## TLS-only 工具

使用当前执行者的 Python 和实际依赖路径。仅有相同 Python 路径不保证带齐 HTTP/2 依赖；应读取当前绑定中的依赖目录，不能临时升级全局 SDK。工具对 `httpx 0.28.1` / `httpcore 1.0.9` 的 trace 契约做限定，并在接网前检查依赖。暂不支持的诊断版本、SOCKS 或 HTTPS 代理会拒绝该诊断；它不会改变现役任务的可运行状态。

`tls-config.json` 使用当前 route 的以下字段：

| 字段 | 值 |
| --- | --- |
| `host`, `port` | 当前实际 HTTPS 主机和端口；不从 source 成功路径猜测 query 路径。 |
| `proxy` | 当前 HTTP CONNECT 代理 URL；原路径直连时才为 null。禁止带账号密码。 |
| `verify`, `trust_env` | true、false；证书验证保持开启，环境变量不隐式换路。 |
| `ca_file` | 可选，当前绑定的 CA 文件绝对路径；不为了通过测试换信任库。 |
| `timeout_seconds` | 每网络阶段最多15秒；不是原 query 的读取期限。 |
| `cases` | 1—4项；每项含唯一 `name`、`mode`（sync/async）、`http2`布尔值、`alpn`（null为库默认，或实际协议列表）。 |
| `bound_transport`, `failure_evidence` | 可附原文件 `{path,sha256}`，会先核哈希；结果用于诊断，不作网络授权。 |

```bash
python3 scripts/nlm_tls_probe.py classify --input /absolute/task/CONNECTION-ATTEMPTS.json --sha256 TRACE_SHA --output /absolute/task/TRACE-CLASSIFICATION.json
python3 scripts/nlm_tls_probe.py probe --input /absolute/task/tls-config.json --sha256 CONFIG_SHA --output /absolute/task/new-tls-probe
```

`classify` 是离线工具，只接受已验证的完整 CONNECT→TLS失败序列；缺字段或不同序列返回 `TRACE_INSUFFICIENT_OR_DIFFERENT`，不自动推断未发送。归还还需要原协调器的进程、锁、请求身份等证据。`probe` 保存版本、SSL验证、ALPN、证书指纹、异常原因链和关闭证据；它不接收 query 内容或凭据。遇到无法证明的异常流，`origin_http_requests` 为 null，不填0。

## 恢复证据预检

旧健康模块要求 `decision.evidence` 中每个顶层附件都是 JSON。恢复依据常包括 `.py`、原始 `.log` 或二进制回执，直接传入会在接网前解析失败。兼容工具把这些原字节 pin 包入 `EVIDENCE.json`，生成新的 `DECISION.json`，保留原决定和附件不动，不扩大 query_cap 或请求身份。

```bash
python3 scripts/nlm_recovery_preflight.py prepare --state /absolute/task/HEALTH.json --state-sha256 HEALTH_SHA --decision /absolute/task/ORIGINAL-DECISION.json --sha256 DECISION_SHA --output /absolute/task/new-recovery-preflight
python3 scripts/nlm_recovery_preflight.py validate --state /absolute/task/FRESH-HEALTH.json --state-sha256 FRESH_SHA --decision /absolute/task/new-recovery-preflight/DECISION.json --sha256 PREPARED_SHA
```

现役 adapter 也可直接调用 `prepare(store.status(), original_decision_ref, new_directory)`；在原共享资源边界用新读出的 `store.status()` 调用 `validate_prepared`，随即沿既有 `store.recover`、READY 与预算准入。预检只能证明给定状态快照和输入兼容，不能证明全账号无在途或该条 READY 尚未被别人消费。实际边界必须保留。校验会拒绝附件哈希变化、暂停失败改变、已返回 ID、已用决定以及改动恢复范围。

此方法保留现役固定健康模块的原字节，不迫使运行中的任务热换组件。安装新工具不自动迁移历史 adapter；先离线回放，再在原流程允许的安全阶段接入。具体日志、账号和文件绝对路径保存在私有任务目录，不写入公开 skill。

## 验证与经验记录

同机存在已授权的网络修复任务时，使用[断流流程中的网络窗口交接](nlm-stream-interruption-recovery.md#同机网络任务的验收窗口)，先接收真实归还和准入暂停回执，再允许主动断线测试。测试实际结束后恢复原 READY，不新增测试 query，也不让正常审读等待无关的只读观察结束。缺少协作交接的主动测试可能中断本已恢复的长答；仅优化 TLS 参数不能解决这一冲突。

维护预约与已交出的窗口须区分。预约尚未交给原网络执行者时，可明确记录撤销未用预约；原 NLM 执行者在新鲜锁边界核无在途后，只解除这一项准入暂停，原查询健康保持并按必要题恢复。旧预约不再允许任何网络操作。窗口已经交出时，必须取得实际操作结束与连接状态回执，不能按时间自动解锁或据对方暂未回复推定未执行。

每次记录：故障层、首次失败时间、原请求实际终态、诊断用时、恢复决定预检、必要请求真实答案与引用、恢复后下一组准入时间、未重复提交数。保存“原因未知”与“恢复已验证”的不同结论。

长响应中断的系统日志必须按原请求的起止窗口读取，保存原时区和统一后的 UTC。接口断链/换网、VPN接口重建、代理配置通知、代理节点切换是不同事件；地址变化可证明换网，不能证明是谁触发。一次实际故障已证实 Wi-Fi 在请求期间断链并重新取得另一网络地址；之后多应用 reset 晚于两条 query 的错误，不能倒置为原因。代理节点日志未覆盖时保留 UNKNOWN，不能改成“async/ALPN不稳定”或要求用户重新登录。

2026-09-25 的真实案例中，原参数和另三组 TLS 对照均通过；历史 TLS 中断根因仍未证实。一次本地恢复失败则确认为把脚本附件当 JSON。修正证据载体后，一条原计划必要题完整返回，随后既有双并发继续。该事实支持恢复流程，不支持永久网络稳定保证。

回归覆盖：非JSON附件/二进制日志、哈希漂移、原请求与额度保持、暂停跨重启、单次恢复准入、未知状态不重置，以及本地环回 CONNECT/TLS 中同步/异步和两种ALPN顺序。环回服务器直接检查 TLS 后收到的源站应用字节为0；无效证书仍失败。这些测试与真实论文轮次分别记账。
